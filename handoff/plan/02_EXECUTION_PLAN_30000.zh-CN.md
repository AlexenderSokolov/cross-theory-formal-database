# 三万道高级数学人类证明题库本地执行计划

> **For agentic workers:** 按本文逐任务执行；已有本地 subagent 流程可直接使用。若使用 Superpowers，采用 subagent-driven-development 或 executing-plans。不要为开始接续再次建立云端会话。

**Goal:** 在可恢复、可追溯、可编辑和质量不退让的前提下，累计得到30,000道合格唯一题。

**Architecture:** 文献原件按作品／版本保存一次；工作智能体在独立题包中整理；一个合并器负责清单、INDEX、全文 SQLite 和 Git 提交。候选／待处理材料与已交付库分离，所有状态可由文件与回执复核。

**Tech Stack:** 当前已验证的 Python 3.12、XeLaTeX、可信 TeX Live 宏包／字体、Poppler、pypdf、SQLite、Git。Lean 为明确分开的后续接纳路线。

**Spec:** [完整标准](01_SCOPE_AND_STANDARDS.zh-CN.md)。本文和标准一起交接，不依赖旧聊天才能执行。

## 全局约束

- 目标是30,000道合格唯一题，不是30,000个链接、定理环境或文件
- 每题完整作者题证与新局部核心、H1/H2/H3及简短依据、精确来源／许可、实际编译、语义去重、INDEX与全文 SQLite 全部保留
- 不做研究性 a/c／跨理论标注，不另起数学审稿，不补造证明
- 保留原编号、原件、旧版本和失败原因；原样通过的证据可以在严格身份一致时复用
- 新题与改动题逐题执行实际 CLI；每500道新增合格题做全库聚合检查和完整证据台账对账
- 全库状态与 Git 由单个合并器写入；候选收集可以并行
- 仅发布有相应权利的安全材料；公开目录不得含会话值、凭据或未授权原生源

## 任务一 接收并固定起点

**输入：** 仓库提交、交接状态文件、已交付 manifest、数据库分段、候选目录、必要材料清单。  
**输出：** 本地接收回执，准确的已交付基数 V，待处理队列。

- [ ] 按命令手册克隆指定分支，并记录 `git rev-parse HEAD`，不要将分支未来更新当作本次已验版本
- [ ] 核对交接清单中的文件数量、SHA-256及材料分类；缺文件先恢复，不能自行宣布旧产物已丢失
- [ ] 离线恢复当前已交付 SQLite，运行其恢复／数据库测试；核对 manifest、INDEX和完整 TeX 行数
- [ ] 分别记录历史来源／PDF证据数量、真实候选ID集合、来源准入、本地通过和远端交付数。不能把旧3195声明当作当前合格基数
- [ ] 阅读当前状态／来源差异记录及全部 hold 原因；原始遗留台账与本次重建台账都保留，当前依据用实际清单
- [ ] 在干净本地编译目录跑代表性样本：原生 TeX、出版转录、含图、中文／特殊字符、三遍稳定、包含自带运行资产。首轮环境稳定后再并发

**验收：** 能打开已交付题目；数据库全文与TeX字节一致；样本真实编译并通过当前门禁；候选不是空目录或仅聊天中的临时路径。

## 任务二 优先消化已有来源

**输入：** catalog 中全部历史／新候选记录，以及已取得且可公开的待处理材料。  
**输出：** 按明确来源块领取的队列、完成位置和分类结果。

- [ ] 先接收已经规范化但未合入的题包，再处理已经来源准入的完整题证；最后处理仅有旧PDF证据／元数据的候选
- [ ] 遗留的 native_tex 字段也要核对；它不是当前完整性、难度或编译通过证明
- [ ] 按作品／章节／确切版本分组，不为同一原件重复下载。先复用已取得的原件与结构化证明边界
- [ ] 每位工作智能体领取互不重叠的来源块；一个块建议2—5篇论文或一个章节范围。记录原文枚举位置，按原顺序筛选，不只挑解析最容易的引理
- [ ] 留用旧稳定ID；新ID由合并器集中分配，不能使用“当前题数+1”。原编号空洞不等于可随意重用
- [ ] 保留所有缺证／低难度／重复／许可／访问／排版 hold，写具体原因与解除条件，避免反复尝试同一失败路线

**验收：** 任意候选可追溯原记录和继续位置；同一来源没有被两个工作者重复领取；没有把辅助结果拆成多个目标题。

## 任务三 单题闭环

**输入：** 一个明确候选与确切原文。  
**输出：** 完整可编辑题证包、来源记录、实际编译／转录证据、明确通过或hold结论。

- [ ] 确认原命题与证明，写2—4句难度依据，并列出真正需要引用的原文标准先修；缺核心证明即换候选
- [ ] 按原生TeX、明确HTML正文、数字PDF、扫描件的顺序选择可忠实处理的表示；表示便利不等于质量或许可更高
- [ ] 追齐主证明调用的所有本篇新核心、附录和续证。不要无限追基础理论，也不要把新构造偷换成先修
- [ ] 从当前原件生成作者、版本、DOI、许可、题面／证明位置及哈希。使用现有完整规范包作为**结构**参考，不复制其题名、归属、难度理由或修改说明
- [ ] 生成独立TeX，保留原语言和数学内容。助手说明分开；必要图、标签和字体全部可追溯，禁止把整段数学证明换成图片
- [ ] 原生源做确定性正文／边界绑定；转录公式对照原页。视觉检查针对缺字、重叠、裁切、错上下标和缺失段落；不要求为仿出版版式而无限调字号或页边距
- [ ] 用禁用shell escape的真实编译得到至少两次成功调用，直到引用稳定；当前辅助程序最多四次。保留实际最后日志，不能只看一个空warning字段
- [ ] 清除未解决引用、缺字、重定义标签和重编译请求；普通Underfull／旧宏警告可在实际可读、已核对条件下保留并明确说明
- [ ] 执行当前 `validate_corpus.py --mode editable-delivery --item ID`。失败条目不入合格清单；修订后重新检查受影响的实际输入
- [ ] 一题完成就保存到候选包；主清单与SQLite由合并器更新，避免多工作者同时改同一个数据库

**验收：** 本地无需原聊天或私有临时目录即可读完整题证；来源、声明的核心和实际正文一致；实际CLI通过，语义唯一性与难度依据可复核。

## 任务四 批次合并与500题检查

**输入：** 若干通过单题流程的隔离包。  
**输出：** 同一版本的题目、manifest、来源、INDEX、全文SQLite、门禁回执和Git提交。

- [ ] 合并器按稳定ID与规范化 DOI／版本／原命题定位检查重复；不同表示归到同一问题身份。候选相似检索只产生待核对对，不自动按标题相似删题
- [ ] 核对相同文献的来源ID和许可证路径；只有源字段实质一致时才共享。逐题排版／修改说明仍保留在各自来源记录
- [ ] 验证所有正向公开清单和实际文件；私有辅助源、抓取网页隐藏字段、不必要历史页图不混入当前公开包
- [ ] 从同一manifest重建SQLite；检查完整性、外键、唯一ID、每条完整TeX、出处字段和数量；不只交一个空schema或只有标题的数据库
- [ ] 新题／改动题运行实际逐题CLI。原样旧题只有正文、来源、许可见证、资产、编译记录、代码与相关投影身份全部一致且有真实既往报告时，才复用旧结果
- [ ] 每500道新增合格题运行当前全库聚合CLI并完整对账。跨500边界本身不要求把所有未变旧题再编译／逐题重跑；全局运行程序变更、缺记录或身份不明时重新执行受影响范围
- [ ] 本地通过后提交，再核验远端提交、关键文件和数据库分段身份。只有远端确认才增加已交付数；把哈希身份核验和完整远端下载核验明确区分
- [ ] 提交粒度不必等到500：建议每25—100道已合格材料形成可恢复提交；500是全局里程碑和常规汇报粒度，不是允许攒着不保存

**验收：** “已交付”只对应一个实际远端提交；中断后可以从提交和队列恢复，不依赖进程内记忆。

## 任务五 扩展来源直至三万

**输入：** 本次整理的原来源目录和新增来源指南。  
**输出：** 轮换的来源块、实际合格产率、版本／许可覆盖和累计目标进度。

先补齐已有约三千条线索的可处理部分，然后扩展明确开放许可的研究论文／高级讲义／完整专著和真实人类形式化项目。研究性期刊、预印本或课程名不是难度保证。考试与无解题单主要用作下界参照或发现线索；未经取得完整人类解答不能计数。

分阶段目标为：接收现有库 → 首个本地20题闭环 → 100题稳定批次 → 500题全局检查 → 3,000 → 5,000 → 10,000 → 20,000 → 30,000。前20题只用于验证本地流程，不是降低标准的试用品；后续继续沿用同一ID与材料。

从每个新来源抽一个小文献块测量：取得全文比例、许可可公开比例、超资格考试且具有独立内容的单元数、核心完整率、TeX/视觉耗时、去重后产率。来源目录的规模不是合格题产率。用实测 `每篇独立合格题数 y` 估计剩余文献量 `(30000−V)/y`，用实际合格题／工作日和成本预测时间。没有测量前不承诺多久能完成，也不把一个形式化库的声明数当作可直接达到三万。

不为凑数放宽难度、改题面、补证明、拆引理或转入无权再分发全文。一个来源产率低或排版成本高，保留处理位置并换来源块，而不是消耗无限上下文。

## 并行与资源建议

建议先4个工作者，稳定后升到8，再依据磁盘、内存、编译排队和真实产率决定是否提高到16。这是本地建议，不是已测吞吐量。可用 gpt-6.1-sol 的低推理档处理清晰的提取、编排与台账；少量疑难转录和版本边界单独升级处理，不把所有题都送去高强度数学复核。

每个工作者写自己的目录。一个来源获取器做缓存和版本固定，一个合并器写全库与Git。无需先引入复杂框架；现有目录、JSONL/CSV队列和SQLite足够开始。后续确有瓶颈再实现小工具。

建议首轮以原生TeX约20分钟、PDF转录约45分钟作为排队预算，而不是质量截止线。超预算转入专门难处理队列，记录完成位置；不得为了时间把未完成题放行。每批记录墙钟时间、实际编译次数、模型用量和失败原因，校正预算。

本地优先常规Git传输，避免把每个截图拆成独立API调用。文件、源文和运行资产按内容哈希去重；同一原件保存一次；只缓存有身份依据的成功证据。大文件采用仓库既有可校验分段／恢复约定或经确认的存储方案，不能把不可恢复临时链接当成备份。

## 五类重点回归检查

1. 候选只有PDF包装或题名时，必须仍处于待处理状态
2. 同一论文两题的许可证／DOI相同但逐题修改说明不同，合并不得把说明串题
3. 换源版本、改一个公式、缺一段附录、缺既往回执，必须使相应旧证据失效
4. 出版转录与nonexclusive原生辅助源混用时，必须保持公开／私有边界和严格归属
5. 真实975→1002等跨500检查，必须保留真计数、实际新题CLI、旧题精确台账及全库聚合，不以伪造非里程碑计数通过

## 只在需要时新增的小工具

以下是后续本地实现任务，不冒称当前仓库已经提供这些命令：

- 来源块领取与续跑：新增 `tools/claim_source_block.py`，接口为读取候选JSONL、独占领取一块、记录owner/lease/继续位置；测试两个进程不能领取同一块，崩溃后可恢复
- 统一安全许可见证：新增 `tools/make_safe_license_notice.py`，从当前条目的固定来源事实生成纯文本；测试复制别的文章署名、ND被误标BY、含隐藏HTML字段均拒绝
- 确定性合并：在现有合并代码成熟后封装 `tools/merge_qualified_packets.py`，输入正向文件清单和规范包，输出隔离的整库与差异报告；测试重复ID、同DOI源字段冲突、缺证明、缺资产和回滚
- 批次台账：封装本次已单独测试的里程碑身份复用逻辑；任何缺失／变化先失败，不修改原数学门禁

每个小工具先写失败测试，再实现并跑通过测试；一次只解决一个实际瓶颈。不要把编写通用平台变成开始收题的前置任务。

### 可选小工具的最小接口与验收

这些接口是给本地实施者的设计约束，尚未作为现成采集命令交付：

| 工具 | 最小接口 | 必须先写的失败测试 |
|---|---|---|
| 来源块领取 | `claim_next(queue_path: Path, owner: str, ttl_seconds: int = 1800) -> Claim | None`；Claim含block_id、来源范围、owner、lease_until | `test_two_workers_cannot_claim_same_block`、`test_expired_claim_recoverable`；不能改变候选合格数 |
| 安全许可见证 | `render_notice(source: SourceAttribution) -> str`；输入只含已核对作者/作品/版本/DOI/来源URL/逐组件许可/证据哈希 | `test_wrong_article_rejected`、`test_missing_or_ND_grant_not_upgraded`、`test_no_raw_form_or_session_values` |
| 规范包合并 | `merge_packets(base: Path, packets: list[Path], output: Path) -> MergeReceipt`；输出必须是新目录 | `test_duplicate_id_rejected`、`test_source_identity_conflict_rejected`、`test_missing_core_or_asset_rejected`、`test_failure_leaves_base_unchanged` |
| 身份证据复用 | `assess_retention(previous: Snapshot, current: Snapshot) -> RetentionDecision`；结果逐项列出复用/重跑理由，不写数学结论 | `test_missing_report_refuses_reuse`、`test_changed_runtime_or_material_refuses_reuse`、`test_real_milestone_requires_fresh_global_gate` |

每个实现任务在隔离分支中先运行新增测试观察预期失败，再实现、运行全部相关测试、用一个真实小批次端到端验证后提交。Snapshot应绑定真实运行报告与确切文件/运行程序身份，不只接收一个“passed=true”。SourceAttribution不能从候选级泛化许可自动推断文件级权限。合并器负责一致性，不替代人工/智能体的语义独立性与难度依据检查。

## 三万题时的GitHub存储安排

不要把本次小规模分段交付机械扩大成每批都提交一份全新巨型数据库。GitHub常规Git阻止超过100MiB的文件，并建议控制仓库规模；官方也明确不建议用Git管理大型数据库。[GitHub大文件说明，2026-10-03核查](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)

建议本地扩展时：Git保留可比较的TeX、清单、索引、来源/权利记录、代码与恢复描述；体量较大的完整SQLite快照和去重原件包按里程碑放到同一已授权仓库的Release资产（受众须与许可和用户授权一致），Git中固定tag、URL、字节数、逐段和整体哈希。官方Release说明当前单资产须小于2GiB、单次最多1,000个资产；按保守上限分段并在实际上传前复核。[GitHub Releases说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

这是后续规模化存储建议，本次并未自动迁移旧历史或开通付费服务。Git LFS如需付费额度，应先明确成本与授权；不得自动购买。也不重写既有Git历史来“节约空间”。当前交接仍按实际随包分段/恢复清单使用，所有大包保留可核验定位，不能只留会过期的临时链接。
